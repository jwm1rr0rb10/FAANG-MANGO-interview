## 0. Фреймворк ответа

Используй одну и ту же структуру для каждой задачи. Интервьюер оценивает **процесс рассуждения и trade-offs**, а не только итоговую схему.

| Шаг | Время (из 45 мин) | Что делать |
|:----|:-----------------:|:-----------|
| 1. Требования | 5 мин | Функциональные требования (3–5 ключевых фич). Нефункциональные: масштаб, latency, доступность vs консистентность, надёжность хранения. Явно скажи, что выходит за рамки задачи. |
| 2. Оценки | 3–5 мин | DAU, QPS (средний и пиковый), соотношение чтения и записи, объём хранения в год, трафик. Считай только то, что влияет на архитектурные решения. |
| 3. API | 3–5 мин | Ключевые эндпоинты или события (REST / gRPC / WebSocket), формат запросов и ответов, пагинация, idempotency keys. |
| 4. Модель данных | 3–5 мин | Сущности, паттерны доступа, выбор SQL или NoSQL с обоснованием, ключ партиционирования. |
| 5. High-level дизайн | 10 мин | Клиенты, балансировщик, сервисы, БД, кэши, очереди. Пройди основные пути чтения и записи. |
| 6. Deep dives | 10–15 мин | 2–3 самые сложные части: горячие ключи, fan-out, консистентность, обработка сбоев. Дай интервьюеру направлять разговор. |
| 7. Итоги | 2–3 мин | Узкие места, единые точки отказа, мониторинг, что изменится при росте нагрузки в 10 раз. |

**Ожидания по уровням:**
- **L4 / Middle:** рабочий дизайн от начала до конца, разумный выбор компонентов.
- **L5 / Senior:** сам ведёт разговор, проактивно объясняет trade-offs, учитывает сбои и масштабирование.
- **L6+ / Staff:** находит настоящую проблему, сравнивает несколько архитектур, учитывает эксплуатацию, стоимость, миграции и влияние на команды.

## 2. Цифры для оценок

| Величина | Примерное значение |
|:---------|:-------------------|
| Обращение к L1-кэшу / к RAM | ~1 нс / ~100 нс |
| Последовательное чтение 1 МБ из RAM | ~10 мкс |
| Случайное чтение с SSD | ~100 мкс |
| Round trip внутри дата-центра | ~0,5 мс |
| Последовательное чтение 1 МБ с SSD | ~1 мс |
| Round trip между континентами | ~100–150 мс |
| Секунд в сутках | ~86 400 ≈ 10^5 |
| 1 млн запросов в сутки | ≈ 12 QPS |
| 100 млн запросов в сутки | ≈ 1 200 QPS (пик ≈ в 2–3 раза больше) |
| Один хорошо настроенный узел БД | ~1K–10K QPS на запись, на чтение больше |
| Один узел Redis | ~100K+ операций в секунду |
| Степени двойки | 2^10 ≈ 1K, 2^20 ≈ 1M, 2^30 ≈ 1B, 2^40 ≈ 1T |
