# Система совместного редактирования в реальном времени: расширенный дизайн с Segment ID и динамическими режимами

## Обзор

Этот файл `README` описывает комплексный дизайн системы совместного редактирования в реальном времени, вдохновлённой `Google Docs`, но расширенной за счёт инновационных возможностей: сегментных идентификаторов (Segment ID) для детализированной блокировки, динамических режимов редактирования в зависимости от количества пользователей, локального кэширования с автосохранением и адаптивного разрешения конфликтов.

Основная цель — построить «лучшую» систему с нуля, устраняя типичные проблемы существующих решений (например, высокий уровень конфликтов в больших группах, проблемы масштабируемости и слабую офлайн-поддержку). Ниже рассматриваются недостатки традиционных подходов `(OT/CRDT)` и способы, которыми данный дизайн их компенсирует.

---

## Ключевые цели

* **Масштабируемость:** поддержка от 2 до 1000+ одновременных пользователей на документ без деградации производительности.
* **Удобство использования:** предотвращение «хаоса редактирования» за счёт блокировок и режимов при сохранении ощущения работы в реальном времени.
* **Надёжность:** использование локального кэша для офлайн-устойчивости и автосохранения для минимизации потери данных.
* **Гибкость:** ручное или автоматическое переключение режимов под разные сценарии (брейншторминг, корпоративное редактирование и т.д.).

---

## Проблемы традиционных систем

* **Перегрузка конфликтами:** в чистых OT/CRDT параллельные правки одного и того же текста приводят к непредсказуемым слияниям (потеря смысла, особенно в rich text).
* **Проблемы масштабируемости:** рассылка каждого изменения 1000+ пользователям перегружает серверы и сеть.
* **Фрустрация пользователей:** отсутствие механизма «занять» участок документа приводит к перезаписи правок в больших командах.
* **Офлайн-разрывы:** задержки синхронизации вызывают расхождение данных.

Данный дизайн улучшает ситуацию, добавляя детализированный контроль поверх OT/CRDT и делая систему адаптивной и устойчивой.

---

## Архитектура системы

### Основные компоненты

Система построена на клиент–серверной архитектуре с распределёнными элементами для масштабирования:

* **Клиент (Frontend):** UI, локальные правки, оптимистичные обновления, локальный кэш для офлайн-работы.
* **Сервер совместной работы:** центральный узел координации операций, разрешения конфликтов и рассылки обновлений. Шардирование по ID документа.
* **Менеджер блокировок:** отдельный сервис (например, Redis) для управления блокировками сегментов и владельцами.
* **Слой хранения:** постоянное хранилище логов операций, снапшотов и метаданных.
* **Real-Time Gateway:** WebSocket-шлюз для низкой задержки.
* **Контроллер режимов:** отслеживает количество пользователей и динамически переключает режимы редактирования.

### Поток данных

1. Пользователь редактирует документ локально → операция ставится в очередь с `segmentID` и `userID`.
2. Клиент отправляет операцию на сервер через WebSocket.
3. Сервер проверяет блокировку → применяет OT/CRDT → рассылает изменения.
4. Клиенты применяют обновления с учётом блокировок.

## Ключевые возможности и улучшения

### 1. Segment ID и детализированные блокировки

#### Принцип работы

* Каждый редактируемый сегмент (слово, предложение, абзац, ячейка таблицы) получает уникальный ID (UUID или Snowflake).
* Операции привязываются к `segmentID`, а не к позициям.
* При начале редактирования менеджер блокировок назначает владельца (TTL, например 30 секунд).
* Остальные пользователи видят сегмент в режиме «только чтение» с визуальными индикаторами.

#### Почему это лучше

* **Предотвращение вмешательства:** блокировки сохраняют атомарность правок и смысл.
* **Масштабирование:** документ делится на сегменты с владельцами — управляемая работа вместо хаоса.
* **Стабильность:** ID не сдвигаются при вставках, в отличие от позиционных правок.

#### Потенциальные проблемы

* Накладные расходы на хранение ID (решается сжатием).
* Deadlock при большом числе блокировок (лимиты на пользователя).
* Гранулярность: слишком мелко — дорого, слишком крупно — мешает совместной работе.

---

### 2. Локальное кэширование и автосохранение

#### Принцип работы

* Клиент хранит состояние документа в IndexedDB.
* Правки применяются локально и ставятся в очередь.
* Автосохранение каждые 5–10 секунд.
* При восстановлении соединения очередь синхронизируется с сервером.

#### Преимущества

* **Офлайн-работа:** редактирование без интернета.
* **Снижение нагрузки:** пакетная отправка правок.
* **Безопасность данных:** защита от сбоев и крашей.

---

#### Решенные проблемы:

- **Нестабильность сети:** В традиционных системах изменения отбрасываются при разрыве соединения; здесь же очередь сохраняется.

- **Задержка:** Локальные операции применяются мгновенно.

--

### 3. Динамические режимы редактирования

Режимы автоматически переключаются в зависимости от числа активных пользователей или вручную.

| Количество пользователей | Режим                    | Основные правила                            | Преимущества             | Компромиссы         |
| -----------------------: | ------------------------ | ------------------------------------------- | ------------------------ | ------------------- |
|                     2–10 | Свободное редактирование | Чистый OT/CRDT, без обязательных блокировок | Быстро, креативно        | Небольшие конфликты |
|                    10–50 | Мягкие блокировки        | Автоблокировка при редактировании           | Баланс свободы и защиты  | Небольшие задержки  |
|                   50–100 | Владение сегментами      | Владелец сегмента, очередь FIFO             | Контролируемая работа    | Ожидание            |
|                  100–500 | Пошаговый режим          | Пакетная обработка                          | Стабильность             | Высокая задержка    |
|                500–1000+ | Строгая модерация        | Одобрение модератора                        | Корпоративная надёжность | Самый медленный     |

## Гибридное разрешение конфликтов (OT + CRDT)

* OT для малых групп и мгновенной консистентности.
* CRDT для больших и офлайн-сценариев.
* Segment ID делает операции коммутативными.
* При конфликте: приоритет по времени, роли или AI-слияние.

## Технологии

* **Frontend:** React + ProseMirror
* **Backend:** Node.js / Go + WebSocket
* **Блокировки:** Redis (Redlock)
* **Хранение:** MongoDB + PostgreSQL
* **CRDT/OT:** Yjs или ShareDB
* **Развёртывание:** Kubernetes, AWS/GCP
* **Мониторинг:** Prometheus
